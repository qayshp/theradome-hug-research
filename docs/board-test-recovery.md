# Board Test and recovery after a firmware update

Use the [installation guide](custom-firmware.md) to choose a HEX and prepare HUG. The recovery below was observed on one EVO LH40 reporting revision `126.6`. Afterward, the owner heard the count play quietly and completed a full treatment. [Device evidence](device.md) · [Live recovery log](volume-settings.md#live-count-readout-update)

## Recover after a successful transfer

1. **Confirm `Success` before changing the USB connection.** If using the HUG GUI, click **Close** on its completion screen and let its follow-up finish. For a timeout, rejected record, or missing `Success` reply, use the [failed-transfer guidance](verification.md#backup-and-recovery). [HUG completion workflow](#what-stock-hug-does)
2. **Check what state the helmet is in.** If the helmet has returned to normal operation, skip to step 5. If it says **“Ready for calibration,”** go to step 4. If it says **“Calibration started,”** leave power connected and wait for completion. Steady green was seen both in Board Test and after calibration, so use the speech or serial reply to resolve an ambiguous light. [Live observations](volume-settings.md#live-count-readout-update)
3. **Leave Board Test if startup is waiting there.** Confirm the `BOARD TEST` banner and read the `D` display. On the startup path that fits this run, field **25** records the setup test and field **29** records calibration. [Startup flags](../model/rebuild.asm#L6573-L6620) · [Recorded parameters](volume-settings.md#calibration-snapshots-across-updates)

   - If both fields are `A5A5`, [exit Board Test](#exit-board-test) and check for normal operation in step 5.
   - If field 25 is `A5A5` and field 29 is `FFFF`, calibration is pending. On our helmet, [Escape](#exit-board-test) produced a yellow pulse. Unplugging USB with the switch untouched then produced **“Ready for calibration.”** [Ready gate](../model/rebuild.asm#L6791-L6822)
   - If field 25 is unset or Board Test keeps coming back, check HUG's completion routine and the [recovery limits](verification.md#backup-and-recovery). This can indicate startup is still waiting on its setup test.

4. **Reconnect power and wait for “Calibration complete.”** Keep the helmet off your head and pointed away from eyes. Reconnect USB without pressing the switch. The helmet said **“Calibration started”** when it detected power from the laptop. The measurements, which can briefly drive the lasers, wait for the charger's **Charged** signal. If your laptop has had trouble charging the helmet, use the wall charger for this reconnect. If it remains waiting for charge and you need to change power sources, disconnect and wait for **“Ready for calibration”** again before connecting the charger. [Calibration states](../model/rebuild.asm#L6989-L7033) · [HUG calibration help](../java/com/screens/FirmwareUpdateMenu.java#L432) · [Theradome charger guide](https://theradome.com/a/docs/troubleshooting/use-and-care-theradome-charger)
5. **Check the result in normal operation.** The test helmet said **“Calibration complete”** and its fresh `D` read showed field 29 set to `A5A5`. If you reopen Board Test to confirm that flag, exit again afterward. Once the helmet is back in normal operation, the off-head, plugged-in short-press count is a simple listening check for the volume fix. [Completion marker](../model/rebuild.asm#L7406-L7434) · [Live playback and treatment results](volume-settings.md#live-count-readout-update)

Escape, unplug, reconnect, and calibration were button-free in this run. Earlier runs also reached calibration without a recorded Escape. For a persistent red pulse, unexpected speech, or an application that HUG cannot identify, check the [LED and speech notes](volume-settings.md#what-the-switch-light-indicated), [Theradome's system error guidance](https://theradome.com/a/docs/troubleshooting/system-error-message), and the [limits of stock recovery](verification.md#backup-and-recovery).

## Recognize and enter Board Test

1. **Find the port.** In Windows Device Manager, look for the helmet's USB Serial Port. Use the assigned COM number on your machine. Windows can see the USB bridge while the application receiver is asleep. [USB driver setup](usb-clock-details.md#windows-arm64-driver-setup)
2. **Connect with HUG.** Select the physical model and click **Next** on the cable screen. On the switch screen, hold the charged, connected helmet's master switch until it speaks the revision. Release it and promptly click **Next** so HUG can search during the timed receive window. Keep the helmet off your head and pointed away from eyes. [Cable screen](../java/com/screens/Connect.java#L134-L152) · [Hold screen](../java/com/screens/ConnectPressButton.java#L123-L140) · [Receive window](../model/rebuild.asm#L10176-L10198)
3. **Probe an existing session with a serial terminal.** Some startup paths open Board Test on their own. Once HUG or the programmer has released the port, use **57,600 baud, 8 data bits, no parity, 1 stop bit, flow control off, and DTR and RTS off**. Listen briefly. If quiet, send one carriage return (`0x0D`) and allow a few seconds for a reply. Look for `BOARD TEST` with `Press [?] for Menu` or `[ESC] to Exit`. Silence leaves the application state uncertain. [Startup menu calls](../model/rebuild.asm#L6651-L6762) · [Serial observations](usb-clock-details.md#what-the-com7-sessions-showed)

Use one program at a time on the port. At a confirmed Board Test prompt, send `?` for the menu and uppercase `D` for the parameter display. Send each as one byte without a line ending. `D` includes the application and bootloader revisions and selected EEPROM values for a before-and-after comparison. [Diagnostic reads and limits](usb-clock-details.md#diagnostic-reads)

A brief switch press in Board Test can start the self-test, energize the lasers, and change saved setup values. Leave the switch alone when checking or exiting an active menu. [Switch handling](../model/rebuild.asm#L6176-L6209) · [Laser test](../model/rebuild.asm#L5427-L5457) · [Pass handler](../model/rebuild.asm#L5937-L5959)

## Exit Board Test

1. Confirm the application menu on the serial terminal. If the terminal accepts hexadecimal input, send **one raw `1B` byte**. Otherwise send the Escape key if the terminal transmits it as ASCII Escape. Send it without a carriage return or line feed.
2. Allow the firmware to return to its startup or operating state. A carriage-return probe that previously returned the banner went quiet after Escape on the tested unit. Close the terminal once you have checked the result. Closing a host port by itself leaves the application free to stay in Board Test.

The archived Escape handler closes the application UART and returns to its caller. The menu can also reach that exit on certain detected charger-loss or switch events. Those routes depend on the current application state. The first unplug and reconnect while green in the latest run left Board Test reachable again. The explicit Escape was the observed exit that advanced that run. ## What stock HUG does

The programming worker closes the port when it returns its result. In the archived GUI, the **Close** button on the completion screen starts a separate routine. It waits a few seconds, reopens the application port at 57,600, and sends a carriage-return probe. On the Board Test exit hint, its Java helper named `sendESCcmd` sends `$` (`0x24`). The archived firmware dispatches that byte to the board self-test. Depending on the response text, HUG may send another carriage return for a temperature prompt. The original Windows and Mac bytecode both contain the same command. A successful board self-test can set EEPROM field 25 to `A5A5` and update the factory-install date. [Transfer worker](../java/SerialCommunication/Communication.java#L193-L220) · [GUI Close action](../java/com/screens/FirmwareUpdateCompleted.java#L245-L256) · [Completion probe and byte](../java/SerialCommunication/Communication.java#L293-L373) · [Board Test dispatch](../model/rebuild.asm#L6063-L6079)

The live transfers used HUG's worker at **115,200 baud**. After worker status `3`, the checked runner stopped. The observed recovery then used literal Escape in the application session at **57,600 baud**, after field 25 was already set. The connected prepared-JAR GUI workflow and the stock Close action remain untested on hardware. The observed wait before probing Board Test did not establish a required delay.
