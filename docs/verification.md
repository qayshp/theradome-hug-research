# LH40 USB tests, offline builds and recovery

The physical unit was a Theradome EVO LH40. Its diagnostics banner said LH80 and its revision reply was 126.6. The archived HUG application image also identifies itself as LH80 and reports application revision 126. The installed flash bytes and board revision remain unverified. [Device and model evidence](device.md)

## Live EVO LH40 tests

| Test | Observed result |
| --- | --- |
| USB serial and revision | The FTDI bridge appeared as COM7. At 57,600 baud, 8N1, with DTR and RTS off, the device reached the `BOARD TEST` menu and returned `PRODUCT CODE REVISION - 126` and `BOOT LOADER REVISION - 6`. This matched the spoken “126.6.” |
| Reopen the port | With USB still connected, a later session reopened COM7 and received no unsolicited bytes during a short listen. A carriage return brought back the diagnostics prompt. The revision query succeeded again without re-entering the login. |
| EEPROM parameters, clock and alarms | The device displayed counters, calibration constants, manufacturing flags, revisions, install-date fields, date and time, and alarm status. Both alarms and the current alarm reported disabled. The parameter screen is a selected display of EEPROM data. |
| Treatment log | The menu returned all 50 retained records. Session numbers were consecutive and the last matched the count shown in the parameter display. The archived writer reads the RTC when it saves a completed treatment. |
| Voice data and effective gain | The menu returned 255 clip-directory slots and 17,234 decoded samples for the first clip. A repeat capture matched those samples exactly. The peak of 4,080 matches zero attenuation in the archived waveform routine. The selected-volume index remains unobserved. Entering diagnostics can itself temporarily force full gain. |
| Clock set and readback | The helmet initially ran about 28 minutes 9 seconds ahead of the laptop. The clock setter acknowledged the write with `Date Set`. Two subsequent reads were within one displayed second of laptop local time. The second read advanced by two seconds. All three alarm-status lines matched their pre-write values. |

The clock exchange used lowercase `t` to read, uppercase `T` to enter the setter, and lowercase `t` again to verify. After the date prompt, the host sent local `YYYY-MM-DD-WW`, with Sunday as `00` and Saturday as `06`. After the time prompt it sent local `HH:MM:SS`. Each field ended in a single carriage return. The completed setter writes the century to EEPROM and updates the RTC. Previously stored treatment timestamps retain the time originally recorded. [Menu and clock setter](../model/rebuild.asm#L3949) · [Treatment record format](../model/eeprom.md) · [Waveform gain](../model/rebuild.asm#L6367)

The archived alarm code uses one hardware alarm for two schedules. The treatment reminder uses a delay in days and requests a voice prompt and green pulse. The charge timeout uses a delay in hours and requests a different prompt and red pulse if ordinary charging is still active. The alert and state transition are visible in the code. The effect on charging current is unverified. [Reminder scheduling](../model/rebuild.asm#L8152) · [Charging-timeout path](../model/rebuild.asm#L7872)

## Treatment readings

The 50 battery readings spanned 3.04–3.87 V. Six rises of 0.31–0.73 V bracketed five intervals of 11, 8, 8, 11 and 8 completed treatments. The two 11-treatment stretches each contained a smaller possible top-up. The log provides one voltage per completed treatment, so charge times and full-charge capacity remain estimates.

At 3.60 V or higher, all 22 current readings fell within 10.43–10.51 mA. The 28 lower-voltage readings ranged from 10.03 to 10.98 mA. Voltage and temperature together accounted for 13.4% of the variation in a linear fit. The fitted temperature slope was sensitive to the influence of unusual readings. The archived code averages 20 ADC conversions, applies a signed calibration offset and divides by 66. The controller targets 10.50 mA on one feedback channel and accepts a range of approximately ±0.55 mA. All 50 readings fall inside that band. The physical wiring behind the feedback channel and the cause of the wider spread at low voltage remain unverified. ## Offline build and volume change

- The Windows and Mac HUG archives contained 629 matching JAR members, including the same stock firmware. Reassembling the recovered source reproduced all 50,816 application bytes at `0x1900–0xDF7F`. Re-encoding those bytes as 794 64-byte Intel HEX data records and one end record reproduced the stock 111,967-byte HEX exactly. A disposable command-menu label change altered exactly four application bytes.
- A second offline build applied the selected volume to the button-requested remaining-time announcement in active and paused modes. It used the chosen shift for both the spoken number and the suffix, then restored the previous effective gain. The application map was unchanged and 48 bytes differed, all in the two button handlers at `0x7360–0x7397`. Applying the source patch again and rebuilding produced the same HEX with SHA-256 `43cc538cf91870e9b0f18f3d5dda60d85923c1c613c95f6281a2409fda2dc967`.
- The assembled patch passed 1,008 instruction-level comparisons. These included 416 requested announcements, 416 automatic checks, 32 double presses, 128 long presses and 16 invalid-index cases. The automatic, double-press and long-press behavior matched stock in the tested cases. The test captures the speech calls and resulting RAM. Playback on a physical helmet and bootloader acceptance remain untested.

## Backup and recovery

The USB menu did not expose a command to export program flash or a complete EEPROM image. The parameter and treatment displays document this unit’s visible state. The HUG HEX is a separate, vendor-provided application image. It omits the bootloader, chip configuration words, unit EEPROM and voice storage. It cannot restore those regions. [Live tests](#live-evo-lh40-tests) · [Archive coverage](firmware.md)

On November 25, 2026, both vendor installers and both URLs used by HUG returned HTTP 200. Both installers and the remote HEX matched the archived copies. The version endpoint returned `version: 126`. The stock updater has a same-version reinstallation path when the running application supplies its revision and responds to the transition into programming mode. HUG then streams its bundled `myTheradome.hex`. [Windows installer](https://apps.theradome.com/downloads/HugApplication.exe) · [Mac package](https://apps.theradome.com/downloads/HugApplication-V200.zip) · [Version endpoint](https://raw.githubusercontent.com/renuraja03/fwupdate/master/fwversion.txt) · [Firmware endpoint](https://raw.githubusercontent.com/renuraja03/fwupdate/master/my.hex) · [Update menu](../java/com/screens/FirmwareUpdateMenu.java#L241)

Recovery from a failed update depends on which code can still run. The normal HUG interface reads the product code revision before proceeding and asks the device to enter programming mode. The archived application's handoff checks battery voltage, acknowledges the request, then resets the controller. No dedicated bootloader-only restore path appears in the traced interface. An enumerated FTDI port establishes the presence of the bridge alone. An interrupted update, a bootloader-only start and stock reinstallation on this LH40 have not been tested. [Version read](../java/SerialCommunication/Communication.java#L141) · [Transition to programming mode](../java/com/screens/FirmwareUpdateFetch.java#L168) · [Application handoff](../model/rebuild.asm#L4582)

A board-level backup is a separate option if the controller and programming pads can be identified. Microchip documents read and export over ICSP for the candidate PIC18 family. A recoverable backup would include independently matching reads of application flash, the bootloader, chip configuration words and unit EEPROM. The programming tool should check coverage and code-protection state. Read-protected regions would leave the backup incomplete. No board-level read was attempted.
