# Enter Board Test and recover after a firmware update

Start with the [build and flash guide](custom-firmware.md) to identify the helmet, build an application HEX, and prepare a HUG bundle. This page covers the serial menu and the steps after a successful transfer. The exact recovery sequence was observed on one EVO LH40 with application revision `126` and bootloader revision `6`. Its USB descriptor and diagnostic banner said LH80. [Device evidence](device.md) · [Live recovery log](volume-settings.md#live-count-readout-update)

HUG sends the HEX to the bootloader at **115,200 baud**. The bootloader writes the image and reports its programming result. The application serves Board Test at **57,600 baud** and handles the startup checks, charger signals, and calibration. The archived HEX contains the application. The bootloader and the unit's preexisting EEPROM contents occupy separate regions. [Image layout](firmware.md) · [Host serial settings](../java/SerialCommunication/Communication.java#L748-L775) · [Firmware state map](../model/firmware-control-map.md)

## Recognize and enter Board Test

1. **Find the helmet's serial port.** Connect with a data-capable USB cable and confirm the USB Serial Port entry in Device Manager. Use the assigned port for your machine. `COM7` was the port on the test laptop. The USB bridge can stay visible while the application receiver is asleep. [Windows driver and USB evidence](usb-clock-details.md#windows-arm64-driver-setup)
2. **Use HUG's normal connection flow for a helmet in ordinary use.** Select the physical model and click **Next** on the USB cable screen. On the switch screen, keep the charged helmet connected, off your head, and pointed away from eyes. Hold the master switch until it speaks the revision. Release it and promptly click **Next** on that screen to start HUG's search. The application speaks first, then enables a timed serial receive window for HUG's login. HUG reporting a connection shows that the helmet communicated. A `BOARD TEST` banner identifies the menu itself. [HUG cable and switch screens](../java/com/screens/Connect.java#L134-L152) · [Hold screen and Next](../java/com/screens/ConnectPressButton.java#L123-L140) · [Hold and receiver entry](../model/rebuild.asm#L10176-L10198)
3. **Check an existing session directly.** Some startup paths enter Board Test on their own when setup flags require service. A port reopen can be quiet while the already-open menu waits for input. Once any programming worker has finished and released the port, open the application port in a serial terminal with **57,600 baud, 8 data bits, no parity, 1 stop bit, flow control off, and DTR and RTS off**. Listen briefly, then send one carriage return (`0x0D`) and allow a few seconds for a reply. `BOARD TEST` with `Press [?] for Menu` or `[ESC] to Exit` identifies the active menu. A silent port leaves the application state uncertain. An otherwise responsive helmet in normal operation can keep its receiver closed. [Startup calls into Board Test](../model/rebuild.asm#L6651-L6762) · [Observed responses and silence](usb-clock-details.md#what-the-com7-sessions-showed)

Use one host client at a time. Close HUG or the previous serial terminal before trying to open the same port from a second program. To inspect a confirmed Board Test session, send `?` for the menu and uppercase `D` for the parameter display. These are single bytes sent without a line ending. The `D` display includes the application and bootloader revisions and selected EEPROM values. It is useful for saving a baseline before a flash and comparing values afterward. [Diagnostic reads and limits](usb-clock-details.md#diagnostic-reads)

Steady orange and steady green both appeared while Board Test could answer. Orange also appeared during the transfer. Use the banner and prompts to identify the active state. While in Board Test, a brief switch press can run the board self-test, which can energize the emitters and change saved setup values. Keep the helmet off your head during this work. [Switch handling](../model/rebuild.asm#L6176-L6209) · [Board Test measurements](../model/rebuild.asm#L5427-L5457) · [Board Test pass handler](../model/rebuild.asm#L5937-L5959)

## Exit Board Test

1. Confirm the application menu on the serial terminal. If the terminal accepts hexadecimal input, send **one raw `1B` byte**. Otherwise send the Escape key if the terminal transmits it as ASCII Escape. Send it without a carriage return or line feed.
2. Allow the firmware to return to its startup or operating state. A carriage-return probe that previously returned the banner went quiet after Escape on the tested unit. Close the terminal once you have checked the result. Closing a host port by itself leaves the application free to stay in Board Test.

The archived Escape handler closes the application UART and returns to its caller. The menu can also reach that exit on certain detected charger-loss or switch events. Those routes depend on the current application state. The first unplug and reconnect while green in the latest run left Board Test reachable again. The explicit Escape was the observed exit that advanced that run. ## What stock HUG does

The programming worker closes the port when it returns its result. In the archived GUI, the **Close** button on the completion screen starts a separate routine. It waits a few seconds, reopens the application port at 57,600, and sends a carriage-return probe. On the Board Test exit hint, its Java helper named `sendESCcmd` sends `$` (`0x24`). The archived firmware dispatches that byte to the board self-test. Depending on the response text, HUG may send another carriage return for a temperature prompt. The original Windows and Mac bytecode both contain the same command. A successful board self-test can set EEPROM field 25 to `A5A5` and update the factory-install date. [Transfer worker](../java/SerialCommunication/Communication.java#L193-L220) · [GUI Close action](../java/com/screens/FirmwareUpdateCompleted.java#L245-L256) · [Completion probe and byte](../java/SerialCommunication/Communication.java#L293-L373) · [Board Test dispatch](../model/rebuild.asm#L6063-L6079)

The checked headless transfers on the test LH40 used HUG's programming worker and ended after it reported status `3`. They skipped the graphical completion routine. The serial recovery below used literal Escape after field 25 was already set. The connected prepared-JAR GUI workflow and the stock Close action remain untested on the physical unit. ## Recover after a successful transfer

1. **Confirm the programming result first.** Keep the cable connected through the write and the loader's `Success` reply. The tested runner logged every row acknowledged, `resp rcvdSuccess`, and worker status `3`. The archived GUI can also display its completion screen for worker status `5`, a fallback based on progress. Check the console for the loader reply. For a timeout, rejected record, or missing success reply, use the [failed-transfer and recovery limits](verification.md#backup-and-recovery). [Worker result and GUI handling](../java/com/screens/FirmwareUpdateProgram.java#L78-L89) · [Worker fallback](../java/SerialCommunication/Communication.java#L873-L881)
2. **Identify the application state after the loader releases the port.** In the GUI workflow, use the completion screen's **Close** button and let its routine finish. For a headless transfer, the application can be checked as soon as it answers on its own baud rate. Look for the Board Test banner or hear the application's normal prompts. The roughly 20-minute wait in the log was an observation. It has no established role as a recovery interval. [Live observations](volume-settings.md#live-count-readout-update)
3. **If Board Test is active, check `D` before leaving it in a post-flash setup state.** On the startup path that fits this run, field **25** records the board test and field **29** records calibration. With field 25 at `A5A5` and field 29 erased (`FFFF`), Escape moved the observed run forward. If field 25 is unset, an early Escape can return to the same setup checks and the menu can reappear. That is a reason to check the result of HUG's completion routine before attempting another flash. The archived HUG connection screen can also invoke the self-test when it finds an active Board Test menu. Using that as a recovery step after a headless transfer remains untested. [Startup flag checks](../model/rebuild.asm#L6573-L6620) · [HUG discovery behavior](java.md#stock-post-transfer-communication) · [Live EEPROM snapshots](volume-settings.md#calibration-snapshots-across-updates)
4. **After Escape, unplug to reach “Ready for calibration” if calibration is pending.** In the tested run the switch changed from steady green to yellow pulses while USB was still connected. With the helmet off your head, unplugged, and the switch untouched, it said **“Ready for calibration.”** The shorter yellow flash matched that transition. The archived marker-check state waits for the charger-absent signal before this announcement. [Calibration-ready gate](../model/rebuild.asm#L6791-L6822)
5. **Reconnect power and wait through “Calibration complete.”** Reconnecting to the same laptop USB port produced **“Calibration started.”** That announcement requires charger detection. Calibration measurements wait separately for the charger's **Charged** signal. Choose a known working charger for this reconnect if laptop charging is uncertain. The routine can briefly enable the emitters. Keep the helmet off your head and connected through the measurements and completion message. If it stays waiting for charge on laptop USB and you need to change power sources, disconnect and wait for **“Ready for calibration”** again before connecting the charger. The firmware can restart the ready check when it loses power before sampling. HUG's help for repeated calibration messages says to use the charger and wait for steady green. [Start, charge and power-loss gates](../model/rebuild.asm#L6989-L7033) · [HUG calibration help](../java/com/screens/FirmwareUpdateMenu.java#L432) · [Theradome charger guide](https://theradome.com/a/docs/troubleshooting/use-and-care-theradome-charger)
6. **Verify the result in normal operation.** The working route from Escape through calibration was button-free. Green alone was ambiguous earlier. The completion announcement and a fresh `D` read with field 29 back at `A5A5` confirmed the save. If you reopen diagnostics for that read, use Escape to close the session again. After recovery, verify the feature you changed with the helmet off your head where possible. The latest build was verified by the quiet short-press treatment count while plugged in. If startup goes straight to normal operation with a valid calibration marker, proceed to the behavior check. [Completion marker write](../model/rebuild.asm#L7406-L7434) · [Recorded listening and serial checks](volume-settings.md#live-count-readout-update)

Two earlier updates completed calibration without a recorded Escape. In one, the helmet reached the ready prompt before a charger reconnect. In the other, a switch press appeared to precede the prompt after a wait on laptop USB. The exact trigger of that earlier run is unresolved. For a persistent red pulse or unexpected speech, consult the [reported LED and speech combinations](volume-settings.md#what-the-switch-light-indicated) and [Theradome’s system error guidance](https://theradome.com/a/docs/troubleshooting/system-error-message). If the application will not answer and normal HUG cannot identify the device, the archived project has no verified bootloader-only recovery procedure.
